## 1. Webkassa API

### 1.1 Орталар және base URL

| Орта | Base URL | Дереккөз |
|---|---|---|
| Sandbox / test | `https://devkkm.webkassa.kz` | `[ЖАНАМА]` (WK-postman, WK-doc) |
| Production | ❌ **таппадым** | — |

`[БҰҒАТТАЛҒАН]` **Production base URL коллекцияда жоқ.** Postman-дағы
барлық 26 сұраныс `devkkm.webkassa.kz`-ке бағытталған. Prod хост
Webkassa техқолдауынан алынады.

`[ЖАНАМА]` (WK-doc) **Динамикалық failover.** `505` қате коды —
«По данному доменному имени сервис временно недоступен». Жауаптың HTTP
header-інде `AlternativeDomainNames` кілті болады, ішінде үтірмен
бөлінген альтернативті хосттар тізімі. Клиент URL-дегі хостты сол
атаулардың біріне ауыстырып, сұранысты қайталауы керек, жауап алынғанша
тізім бойынша жүріп өтеді.
→ **Бұл дегеніміз: base URL-ды конфигте hardcode етуге болмайды, ол
runtime-да өзгеретін тізім.**

Тіркелу: `https://devkkm.webkassa.kz/` — тест кабинетінде тіркеліп,
email растап, «Кабинет интегратора» бөліміне кіру керек `[ЖАНАМА]`
(promo.webkassa.kz іздеу сниппеті; сайттың өзі бұғатталған).

### 1.2 Аутентификация — екі қабатты

**1-қабат: `x-api-key` HTTP header (жүйені сәйкестендіру).**

`[ЖАНАМА]` (WK-postman, «Авторизация» бөлімінің сипаттамасы):
> «Для взаимодействия с API Webkassa выдается специальный ключ (API-KEY) —
> это строка специального формата, идентифицирующий систему... Для каждой
> системы создается два API-KEY: для тестирования и для использования в
> продуктивной среде. Каждый запрос к API Webkassa должен содержать
> API-KEY... Получить API-KEY... можно через каналы связи с технической
> поддержкой Webkassa.»

Формат мысалы: `WKD-9BCE5F1E-AE33-4F39-BF8B-ABDBF2376398` (`WKD-` префиксі
+ UUID).

**2-қабат: `Token` (пайдаланушы сессиясы) — body ішінде, header емес.**

```http
POST https://devkkm.webkassa.kz/api/v4/Authorize
x-api-key: WKD-XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
Content-Type: application/json

{ "Login": "email@email.com", "Password": "Asdzxc1!" }
```

Сәтті жауап:
```json
{ "Data": { "Token": "b20a7c5e22844c50bf8389fe09c6b8c2" } }
```

`[ЖАНАМА]` (WK-doc, «АВТОРИЗАЦИЯ» бөлімі) — токеннің жарамдылығы:
> «Токен действует до следующей операции авторизации. Рекомендуемая
> периодичность переавторизации (запрос нового токена) — пользовательская
> сессия, но не реже раза в сутки. В случае получения ошибки с кодом 2
> (Срок действия сессии истек) для продолжения работы необходимо вызвать
> метод Авторизации.»

**Жобаға түйін `[БОЛЖАМ]`:** нақты TTL жарияланбаған. Дұрыс стратегия —
токенді тәулігіне кемінде бір рет жаңарту **және** `Code: 2` немесе
`Code: 3` алынғанда бір рет автоматты re-auth жасап, сұранысты қайталау.
Ол қайталау **идемпотентті болуы шарт** (сол `ExternalCheckNumber`-мен).

Барлық кейінгі сұраныстарда `Token` — **body-дың бірінші өрісі**
(`Authorization` header ЕМЕС).

### 1.10 Идемпотенттілік — `Code: 14` семантикасы (⭐ жобаның ең маңызды бөлігі)

`[ЖАНАМА]` (WK-doc, тікелей цитата):
> «**14 — Дублирующийся код системы-источника.** Ошибка возвращается **в
> качестве предупреждения**, о том, что данный чек/информация уже был
> передан в систему Webkassa. ... если в теле запроса содержится чек,
> который уже был передан в Webkassa ранее, то при получении данной ошибки
> **повторное выполнение запроса не требуется**.»

**Интерпретация:**
* `ExternalCheckNumber` — **client-generated идемпотенттілік кілті**.
  Жобаның CLAUDE.md §5.3-тегі принципімен дәл сәйкес келеді.
* `Code: 14` — **қате емес, растау**. Оны сәтті нәтиже ретінде өңдеу керек.
* ⚠ **БІРАҚ:** `Code: 14` жауабында **фискалдық белгі (`CheckNumber`)
  ҚАЙТАРЫЛМАЙДЫ.** Демек, желі үзілгенде («жіберілді ме, жоқ па?»
  белгісіз күй) біз чекті қайта жіберіп, `14` алсақ — фискалдық белгіні
  басқа жолмен қалпына келтіруіміз керек.
* **Қалпына келтіру жолы `[БОЛЖАМ]`:** `/api/v4/Ticket/PrintFormat`
  эндпоинті кірісінде `ExternalCheckNumber` + `CashboxUniqueNumber`
  қабылдайды → сол арқылы бұрын тіркелген чектің баспа формасын алуға
  болады. Балама — `/api/v4/Check/History` (ауысым бойынша) немесе
  `/api/v4/Reports/ControlTape` (жауабында `ExternalOperationId` өрісі
  бар — біздің кілтпен салыстыруға жарайды).
  ⚠ Бұл жолдардың `CheckNumber`-ды қайтаратыны **тестпен тексерілмеген**
  (§8).
* `ExternalCheckNumber` **міндетті** болды: v22 нұсқасынан бастап
  «Введена обязательность параметра ExternalCheckNumber в методах
  "Обработка операций по чеку", "Внесение и изъятие наличных"»
  `[ЖАНАМА]` (WK-doc, версиялар тарихы).

### 1.11 Rate limit, тайм-аут, retry

`[БҰҒАТТАЛҒАН]` **Rate limit туралы ешқандай мәлімет ТАППАДЫМ.**
v35 құжатында да, Postman коллекциясында да «запросов в секунду»,
«лимит», «timeout», «throttl», `429`, `Retry-After` сөздерінің ешқайсысы
кездеспейді (grep-пен тексерілді). Webkassa-дан ресми түрде сұрау керек.

Ресми түрде бекітілген жалғыз retry-саясаты — **кері бағыттағы**
(Webkassa → біздің жүйе) курьер уведомлениесі үшін:
> «Webkassa повторяет отправку уведомления через 12 часов. Общее число
> попыток отправки уведомления с учетом повторов: 3 раза.»
`[ЖАНАМА]` (WK-doc §18.2).

`[БОЛЖАМ]` Клиент жағындағы ұсынылатын саясат:
* Тайм-аут: connect 5 s, read 30 s (фискалдау синхронды, ОФД-ға дейін барады).
* Retry тек **идемпотентті** сұраныстарға (`ExternalCheckNumber` бар) және
  тек желі қатесі / 5xx / `505` жағдайында. Экспоненциалды backoff.
* `1`, `4`, `5`, `6`, `7`, `8`, `10`, `12`, `13` — **ешқашан retry жасамау**.
* `2`, `3` — бір рет re-auth + бір рет қайталау.

чектің толық баспа формасын **дайын күйінде** қайтарады. **Бұл 17
реквизиттің дұрыс құрастырылуы үшін жауапкершілікті ОФД жағына
ысырады.** Өз баспа формамызды жазу — тәуекел. Бірақ дизайн еркіндігін
жоғалтамыз.
→ **Ұсыныс `[БОЛЖАМ]`: MVP-де `TicketPrintFormat`-ты сол күйінде
пайдалану**, өз рендерімізді Фаза 3-тен кейін ғана қарастыру.

### 3.4 НКТ / NTIN — ⚠ БАҒЫТ ӨЗГЕРУІ МҮМКІН

`[ЖАНАМА]` (WK-postman) — техникалық жағы: `Positions[]` ішінде
`GTIN`, `NTIN`, `ProductId` өрістері бар; **`WarehouseType = 1`
(виртуалды қойма) болғанда ғана міндетті**.

`[ЖАНАМА]` ⚠⚠ **Маңызды жаңалық** (pro1c.kz, «Новые требования к
содержанию чека ККМ (опубликован проект приказа) от 20.04.2026»):
> «Приказом планируется внести изменения в требования к содержанию чека
> ККМ: **исключается абзац об отображении наименования товара в
> соответствии с НКТ в электронном виде**.»

→ **Бұл жобаның CLAUDE.md §3-тегі болжамына қайшы келеді.** CLAUDE.md-де
НКТ бойынша атау мен NTIN — сөзсіз міндет деп жазылған. Ал 2026-04
жобасы бойынша ол талап **алынып тасталуы мүмкін**.

⚠ **WebFetch сәтсіз (pro1c.kz бұғатталған), тек іздеу сниппеті бар.
Бұйрықтың қабылданғанын/қабылданбағанын білмеймін.**
→ `[БҰҒАТТАЛҒАН]` §8.

`[БОЛЖАМ]` **Архитектуралық шешім:** NTIN/GTIN-ді домен моделінде
**опциялық** өріс ретінде ұстау, чек құрастыруда «толтыруға болады,
міндетті емес» логикасымен. Егер талап қайта енгізілсе — адаптерде бір
жалауша қосу жеткілікті болады.

**ГБД НКТ-ға тікелей API `[БҰҒАТТАЛҒАН]`** — таппадым. Webkassa
құжаттамасында НКТ-дан атау тарту әдісі жоқ; тек `GTIN`/`NTIN`-ді
**біз беретін** өрістер бар. Яғни CLAUDE.md-дегі «атау ОФД сервистері
арқылы ГБД НКТ-дан тартылады» деген тұжырым **Webkassa API-де
расталмады**.

### 3.5 Маркировка (Data Matrix)

`[ЖАНАМА]` (WK-postman) — техникалық арна бар:
* `Positions[].Mark` — бір код (Count = 1 болғанда).
* `Positions[].MarkList[]` — кодтар массиві, **тек 2.0.3+ протоколында**.
* Бір позицияда екеуінің тек біреуін пайдалануға болады.
* Мысалдағы код: `0104603276013765213A8B06OMH52K291KZF092TH...` —
  GS1 Data Matrix форматы.
* re:Kassa-да ұқсас өріс — `commodity.exciseStamp` `[ЖАНАМА]`.

`[БҰҒАТТАЛҒАН]` **ТАППАДЫМ:**
* Маркировка міндетті тауар топтарының 2026 жылғы ресми тізімі
  (сыра, темекі, аяқ киім, жеңіл өнеркәсіп, мотор майлары, дәрі-дәрмек —
  бұлар CLAUDE.md-ден алынған, мен растай алмадым).
* «Танба» / ISMET жүйесінің API құжаттамасы.
* Кодтарды сатылымнан шығару (вывод из оборота) рәсімі.
* Маркировка кодын ОФД-ға беруден бөлек, «Танба»-ға тікелей беру
  міндеті бар ма — белгісіз.

⭐ **Сегмент үшін ықтимал жақсы жаңалық `[БОЛЖАМ]`:** біздің MVP
сегменті — кафе/кофехана/шағын дүкен. Онда маркировка негізінен **сыра**
арқылы келеді. Егер MVP-ге сыра сатылатын нүктелерді кіргізсек,
Data Matrix сканерлеу + `MarkList` — **міндетті**. Кофехана үшін
маркировка мүлдем қажет болмауы мүмкін.

### 3.6 72 сағаттық автономды режим

`[ЖАНАМА]` (WK-doc, `Code: 18`) — **техникалық жағы нақты:**
> «Продолжительность работы в автономном режиме превышает **72 часа**.
> Для продолжения работы с кассой необходимо подключение к ОФД.»
> «Ошибка возвращается при попытке провести кассовую операцию при
> истечении максимального срока работы кассы в автономном режиме
> (72 часа без соединения с ОФД).»

Рекомендация: «необходимо остановить отправку запросов по кассе...
проверить оплату в ОФД и наличие связи... Возобновление отправки
запросов необходимо осуществить после того, как будут оплачены услуги
ОФД и налажено интернет-соединение.»

`[ЖАНАМА]` (wk.gke.kz, интегратор): автономды режимге өтудің 2 себебі —
(1) ОФД қызметі қолжетімсіз; (2) ОФД қызметі төленбеген. Байланыс
қалпына келгенде чектер ОФД-ға автоматты жүктеледі.

`[БҰҒАТТАЛҒАН]` **ТАППАДЫМ:**
* Заңдағы **нақты формулировка** (қай бап, қандай сөзбен).
* 72 сағаттың **санағы қашан басталады** — соңғы сәтті берілістен бе,
  әлде байланыс үзілген сәттен бе?
* 72 сағаттан асқанда **чек заңды тұрғыдан жарамсыз бола ма**, әлде тек
  ККМ бұғатталады ма?
* Байланыс қалпына келгендегі **жіберу мерзімі** (қанша уақыт ішінде).
* Айыппұл бар ма.

`[БОЛЖАМ]` Webkassa-ның мінез-құлқынан: 72 сағат — **ККМ-ді бұғаттау**
шарасы, чектің жарамдылығы емес. Чек автономды режимде де жарамды
(§3.3-те 17-реквизит — «автономды белгі» — заңда көзделген, демек заң
автономды чекті таниды).

## 4. Офлайн режим ережелері

### 4.1 ⭐⭐ ЕҢ МАҢЫЗДЫ АРХИТЕКТУРАЛЫҚ ТҰЖЫРЫМ: екі бөлек офлайн бар

Webkassa API-дегі **екі бөлек жалауша** мұны айқын көрсетеді
`[ЖАНАМА]` (WK-postman):

| Жалауша | Мағынасы |
|---|---|
| `OfflineMode` | **Осы нақты чек** автономды режимде жасалды |
| `CashboxOfflineMode` | **Касса тұтастай** автономды режимде тұр |

Және `Cashboxes` жауабындағы `IsOffline`.

**Бұл жалаушалар «Webkassa ↔ ОФД» буынына қатысты, «POS ↔ Webkassa»
буынына емес.** `[ЖАНАМА]` (WK-doc, «ОБРАБОТКА ОПЕРАЦИЙ ПО ЧЕКУ»):
> «В случае работы в автономном режиме фискальный признак генерируется
> **системой Webkassa**.»

Яғни фискалдық белгіні автономды режимде **бұлттағы Webkassa** жасайды,
біздің POS емес.

**Демек:**

```
[POS Flutter] ──(A)── [Webkassa cloud] ──(B)── [ОФД] ── [КГД]
                 ↑                          ↑
        мұнда офлайн болса —      мұнда офлайн болса —
        ФИСКАЛДЫҚ БЕЛГІ ЖОҚ       72 сағат автономды режим,
        → ЧЕК ЖАСАЛМАЙДЫ          белгіні Webkassa өзі береді
```

`[БОЛЖАМ]` ⚠⚠ **Егер біз Webkassa-ның бұлттық API-ін тікелей
пайдалансақ, интернетсіз ЕШҚАНДАЙ фискалдық чек шығара алмаймыз.**
Бұл жобаның **1-дифференциациясын (offline-first) толықтай жоққа
шығарады.**

### 4.2 Ықтимал шешім: WK.LocalServer

`[ЖАНАМА]` `VitalyKravtsov2016/OposWebkassa` репозиторийінің `doc/Webkassa/`
папкасында мына файлдар бар (файл атаулары көрінеді, мазмұны ашылмады):
* `WebCash_LocalServer_2.0.5_CORE5.7z`
* `WebCash_LocalServer_2.1.3_CORE5.zip`
* `WebCash_LocalServer_2.1.6_CORE5.zip`
* `WebCash_LocalServer_2.1.6_CORE5_SRC.zip`
* `Инструкция по запуску WK.LocalServer в Windows_2.0.1.pdf`
* `CashBoxStateRequest.json`, `CashBoxStateResponse.json` (+2 нұсқа)

→ Webkassa-да **жергілікті сервер компоненті** бар. Ол, сірә, чектерді
жергілікті фискалдап, кейін синхрондайды.

⚠ **Бірақ файл атауында «в Windows» тұр** → **Android/iOS-та жұмыс

→ `[БҰҒАТТАЛҒАН]` — вендордан сұрау керек (§8).

### 4.3 Дубликаттан қорғау механизмі

`[ЖАНАМА]` (WK-doc + WK-postman):
* Жалғыз механизм — **`ExternalCheckNumber`** (чекте) және
  **`externalCheckNumber`** (ақша операциясында).
* Екеуі де **міндетті** (v22-ден бері).
* Қайталанғанда `Code: 14` қайтады — «предупреждение», қате емес.
* `ControlTape` жауабында `ExternalOperationId` өрісі бар — біздің
  кілтпен салыстырып, кезекті қалпына келтіруге жарайды.

**Ұсынылатын кілт `[БОЛЖАМ]`:** client-generated UUID v4, чек жасалған
сәтте бір рет генерацияланып, SQLite-та сақталады және **ешқашан
өзгермейді** — retry болса да сол кілт. Postman мысалдарында дәл UUID
форматы қолданылған (`e4c89243-82nb-4622-9131-c8a93795d1ec`).

### 4.4 ⚠ Офлайн уақыт өрісі — ЖОҚ

`[ЖАНАМА]` (grep-пен тексерілді): `check` сұранысында
**`OperationDate` / `DateTime` сияқты клиенттік уақыт өрісі ЖОҚ**.
Фискалдық уақытты **сервер белгілейді**.

Жалғыз клиенттік күн-уақыт өрісі — `ReturnBasisDetails.DateTime`, ол да
**негіз-чектің** уақыты, ағымдағы операцияның емес.

⚠⚠ **Салдары:** POS 3 сағат офлайн болып, кейін кезекті жіберсе,
барлық чектер **жіберілген уақытпен** фискалданады, сатылған уақытымен
емес. Бұл — есеп пен аудит үшін елеулі мәселе.

`[БОЛЖАМ]` re:Kassa-да `dateTime` өрісі **бар** (§2.3) — бұл жағынан
re:Kassa артық. Бірақ оның да сервер қабылдай ма, әлде елемей ме —
белгісіз.

### 4.5 Кезекті жіберу тәртібі

`[БОЛЖАМ]` (дереккөз жоқ, талдаудан шығады):
1. **Реттілік міндетті.** `CheckOrderNumber` (ауысым ішіндегі реттік
   нөмір) серверде беріледі. Чектерді араластырып жіберсек, реттілік
   бұзылады.
2. Сондықтан кезек — **қатаң FIFO, бір ағынды (single-flight)**, әр
   касса үшін бөлек.
3. Бір чек `Code: 14` алса → сәтті деп белгілеп, келесіге өту.
4. Бір чек қалпына келмейтін қатеге тап болса (`9` — деректер қате) →
   **кезекті тоқтату, кассирге көрсету**. Автоматты «өткізіп жіберу»
   болмауы керек — фискалдық аудит бұзылады.
5. `Code: 18` (72 сағат) → кезекті толық тоқтату.

### 4.6 Уақыт ауытқуы

`[ЖАНАМА]` Webkassa `DateTimeUTC` өрісін таймзонамен қайтарады
(`14.09.2025 16:55:37 +05:00`).
→ Жергілікті БД-да фискалдық уақытты **сервер бергенін** сақтау керек,
құрылғының уақытын емес (CLAUDE.md §5.6-мен сәйкес). Құрылғы уақытын тек
UI-да «сатылым сәті» ретінде бөлек өріспен көрсету.

### 6.1 Орналасуы

### 6.2 Интерфейс

```dart
/// Provider-agnostic fiscal gateway contract.
/// Implementations live in /services/fiscal. No provider name, endpoint,
/// or vendor error code may leak through this interface.
abstract interface class FiscalProvider {

  // ---- capabilities -------------------------------------------------
  /// Static description of what this provider supports.
  /// Callers MUST branch on this instead of on the provider's identity.
  FiscalCapabilities get capabilities;

  // ---- session ------------------------------------------------------
  /// Establishes a provider session. Implementations own token caching
  /// and silent re-authentication.
  /// Webkassa: POST /api/v4/Authorize (+ x-api-key header).
  /// re:Kassa: POST auth/login?apiKey=... -> Bearer token.
  Future<FiscalResult<FiscalSession>> openSession(FiscalCredentials creds);

  // ---- device state -------------------------------------------------
  /// Cash register health: registration status, licence expiry,
  /// whether the register is currently in autonomous (offline-to-OFD) mode.
  /// MUST be called before opening a shift.
  /// Webkassa: /api-portal/v4/cashbox/client-info + /api/v4/Cashboxes.
  /// Legal driver: art. on KKM state register + 72h autonomy limit.
  Future<FiscalResult<CashRegisterState>> fetchRegisterState(
    CashRegisterId register,
  );

  // ---- shift --------------------------------------------------------
  /// Ensures a shift is open. On providers with no explicit open-shift
  /// endpoint (Webkassa, re:Kassa) implementations resolve the current
  /// shift and report it; they MUST NOT emit a phantom fiscal operation.
  /// Legal driver: a shift may not exceed 24 hours.
  Future<FiscalResult<ShiftState>> ensureShiftOpen(CashRegisterId register);

  /// Interim report, no reset. Sourced from the OFD, therefore NOT
  /// available while the POS itself is offline.
  Future<FiscalResult<ShiftReport>> xReport(CashRegisterId register);

  /// Closes the shift and returns the Z-report (report with reset).
  /// Legal driver: mandatory fiscal operation; must be produced within 24h.
  Future<FiscalResult<ShiftReport>> closeShift(
    CashRegisterId register, {
    required IdempotencyKey key,
  });

  // ---- receipts -----------------------------------------------------
  /// Registers a fiscal receipt: sale, purchase, return of sale,
  /// return of purchase. `request.basis` is REQUIRED for both return
  /// kinds under OFD protocol 2.0.3+.
  /// Legal driver: every cash settlement must be fiscalised.
  Future<FiscalResult<FiscalReceipt>> registerReceipt(
    ReceiptRequest request, {
    required IdempotencyKey key,
  });

  /// Cash in / cash out (inkassatsiya). A fiscalised operation.
  Future<FiscalResult<CashOperationResult>> registerCashOperation(
    CashOperationRequest request, {
    required IdempotencyKey key,
  });

  // ---- recovery (idempotency) ---------------------------------------
  /// Resolves an operation whose outcome is unknown after a network
  /// failure, using ONLY the client-generated key. This is the method
  /// that makes retry safe.
  /// Webkassa: /api/v4/Ticket/PrintFormat by ExternalCheckNumber,
  ///           fallback /api/v4/Reports/ControlTape (ExternalOperationId).
  /// re:Kassa: ticket lookup by externalId.
  Future<FiscalResult<FiscalReceipt?>> lookupByIdempotencyKey(
    CashRegisterId register,
    IdempotencyKey key,
  );

  // ---- print --------------------------------------------------------
  /// Returns the receipt as provider-rendered print lines. Preferred over
  /// rendering ourselves: the provider is responsible for the 17 mandatory
  /// requisites.
  /// `primary` / `secondary` map to receipt languages; primary defaults
  /// to kk-KZ for this project.
  Future<FiscalResult<PrintDocument>> fetchPrintForm(
    CashRegisterId register,
    IdempotencyKey key, {
    required PaperKind paper,
    required Locale primary,
    Locale? secondary,
  });
}
```

### 6.3 Қосалқы типтер

```dart
/// Client-generated, persisted, immutable. The single anti-duplication
/// mechanism across every provider found in this research.
extension type const IdempotencyKey(String value) {
  // UUID v4, generated once when the receipt is created locally,
  // stored in SQLite, reused for EVERY retry, forever.
}

final class FiscalCapabilities {
  /// Provider accepts a client-supplied operation timestamp, so queued
  /// offline receipts keep their real sale time.
  /// Webkassa: false (no such field). re:Kassa: true (dateTime object).
  final bool supportsClientTimestamp;

  /// Provider exposes an explicit cancel/void of a registered receipt.
  /// Webkassa: false (correction is done as a return receipt).
  final bool supportsReceiptVoid;

  /// Marking codes may be sent as an array within one position
  /// (OFD protocol 2.0.3+); otherwise one code per position.
  final bool supportsMarkArray;

  /// Return receipts require the basis receipt's details (2.0.3+).
  final bool requiresReturnBasis;

  /// Payment method codes this provider understands, mapped from our
  /// domain PaymentMethod. Kaspi QR mapping is UNVERIFIED — see §8.
  final Set<PaymentMethod> supportedPaymentMethods;

  /// Hard limit after which the register refuses operations without OFD.
  final Duration autonomousModeLimit; // Webkassa: 72h
  final Duration maxShiftDuration;    // 24h by law
}

/// Every failure is classified into a retry policy, so the outbox never
/// has to know a vendor error code.
enum FiscalFailureKind {
  /// Retry the very same request with the same idempotency key.
  transientNetwork,        // timeouts, 5xx, host failover (Webkassa 505)

  /// Re-authenticate once, then retry with the same key.
  sessionExpired,          // Webkassa 2, 3

  /// Already accepted by the provider. TREAT AS SUCCESS, then call
  /// lookupByIdempotencyKey to recover the fiscal sign.
  duplicateAccepted,       // Webkassa 14

  /// Shift must be closed first, then retry.
  shiftExpired,            // Webkassa 11

  /// No open shift.
  shiftNotOpen,            // Webkassa 12, 13

  /// Autonomy window exhausted. STOP the whole outbox, alert the cashier.
  autonomyLimitExceeded,   // Webkassa 18

  /// Register blocked / not activated / licence expired. Cannot be fixed
  /// from the app.
  registerUnavailable,     // Webkassa 6, 7, 10

  /// Our request is malformed or the operator lacks rights.
  /// NEVER retry; surface to the operator.
  permanentRejection,      // Webkassa 1, 4, 5, 8, 9
}

sealed class FiscalResult<T> {
  const FiscalResult();
}
final class FiscalOk<T> extends FiscalResult<T> {
  final T value;
  /// True when the provider fiscalised this in autonomous (offline-to-OFD)
  /// mode. MUST be printed on the receipt (mandatory requisite #17).
  final bool autonomous;
  const FiscalOk(this.value, {required this.autonomous});
}
final class FiscalFailure<T> extends FiscalResult<T> {
  final FiscalFailureKind kind;
  final String providerCode;   // opaque, for logs only
  final String message;        // operator-facing, already localised
  final Duration? retryAfter;
  const FiscalFailure(...);
}

final class FiscalReceipt {
  final String fiscalSign;        // Webkassa CheckNumber
  final int orderNumberInShift;   // CheckOrderNumber
  final int shiftNumber;
  final DateTime fiscalisedAtUtc; // server time, NOT device time
  final Uri verificationUrl;      // TicketUrl -> becomes the QR
  final bool autonomous;          // OfflineMode
  final CashRegisterIdentity register; // ЗНК, РНК, address kk+ru, OFD name
  // ↓ persisted forever: needed as ReturnBasisDetails for any future return
  final Money total;
}
```

### 6.4 Офлайн кезегін өрнектеу

Интерфейс **синхронды және тікелей**. Кезек — интерфейстен **тыс**,
`/apps/pos` ішінде:

```dart
/// Durable, per-register, strictly FIFO, single-flight outbox.
/// Lives in SQLite so it survives a crash mid-fiscalisation.
abstract interface class FiscalOutbox {
  /// Enqueues an operation. Returns immediately; the receipt is NOT yet
  /// fiscal. The UI must show "фискалдау күтілуде".
  Future<void> enqueue(PendingFiscalOperation op);

  /// Drains the queue in order. Stops (does not skip) on
  /// permanentRejection / autonomyLimitExceeded / registerUnavailable.
  Future<void> drain(CashRegisterId register);

  Stream<OutboxState> watch(CashRegisterId register);
}

final class PendingFiscalOperation {
  final IdempotencyKey key;       // generated ONCE, never regenerated
  final int localSequence;        // logical order; device clock not trusted
  final DateTime deviceCreatedAt; // informational only
  final FiscalOperationPayload payload;
  final OutboxStatus status;      // pending | inFlight | fiscalised | blocked
  final String? fiscalSign;       // filled after success or after lookup
  final int attemptCount;
  final String? lastProviderCode;
}
```

**Кезектің инварианттары `[БОЛЖАМ]`:**
1. `IdempotencyKey` кезекке қосылған сәтте бір рет жасалады, retry-да
   **ешқашан** жаңартылмайды.
2. Бір кассаға бір мезгілде тек бір `inFlight` операция (`CheckOrderNumber`
   реттілігі бұзылмас үшін).
3. `inFlight` күйінде процесс құласа → қайта іске қосылғанда алдымен
   `lookupByIdempotencyKey`, содан кейін ғана қайта жіберу.
4. `duplicateAccepted` → бірден `lookupByIdempotencyKey` → `fiscalised`.
5. `blocked` күйде кассирге көрінетін баннер + Z-есеп жасауға тыйым.
6. **Ешқашан «өткізіп жіберу» жоқ** — фискалдық аудит үзілмеуі керек.

### 6.5 ⚠ Интерфейстің шешпейтін мәселесі

Бұл интерфейс **POS ↔ ОФД** буынындағы офлайнды шешпейді (§4.1).
`enqueue` чекті сақтайды, бірақ **фискалдық белгісіз чекті сатып
алушыға беруге бола ма — заң тұрғысынан белгісіз** (`[БҰҒАТТАЛҒАН]`).

Мүмкін болатын үш жол `[БОЛЖАМ]`:
* **A.** WK.LocalServer / ұқсас жергілікті компонент (§4.2) — Windows-қа
  байлану қаупі.
* **B.** Kassa-ның өз ОФД-мен тікелей интеграциясы (2.0.3 протоколы
  бойынша) — біз өзіміз ККМ моделі болып тізілімге кіреміз. Ең үлкен
  жұмыс, бірақ ең толық бақылау және ТИС жолы да осы.
* **C.** Офлайнды тек «тапсырыс қабылдау» деңгейінде қалдырып,
  фискалдауды міндетті түрде онлайн жасау — дифференциацияны жоғалту.

→ **Бұл — Фаза 2 басталмас бұрын шешілуі керек №1 сұрақ.**

## 10. Фаза 2-ге тікелей әсер ететін 6 талап

1. **SQLite схемасына:** әр фискалданған чек үшін `check_number`,
   `fiscal_datetime_utc`, `cashbox_reg_number`, `total`, `is_offline`
   өрістерін **мәңгі** сақтау — қайтару чегінде `ReturnBasisDetails`
   ретінде керек (2.0.3 талабы).
2. **Идемпотенттілік:** `IdempotencyKey` (UUID v4) — чек жасалғанда бір
   рет, `outbox` жазбасының бөлінбейтін бөлігі. Retry-да ешқашан
   жаңартылмайды.
3. **Money:** `Tax` өрісі API-де `decimal` (`53.57`). Біздің
   `Money` integer тиын/тенге болғандықтан, **адаптер шекарасында
   айналдыру** керек және дөңгелектеу ережесі (`RoundType`) конфигтен
   келуі керек. ҚҚС мөлшерлемесі (12 → 16%) **hardcode етілмейді**.
4. **Ауысым таймері:** 24 сағаттық шектеу — доменде емес, POS
   қабатында; кассирге 23:00-де ескерту.
5. **Баспа:** MVP-де `TicketPrintFormat[]`-ты сол күйінде пайдалану
   (17 реквизит үшін жауапкершілік ОФД-да). `Type=2` жолын QR ретінде
   рендерлеу міндетті.
6. **Тіл:** `Accept-Language: kk-KZ` + `Secondary-Language: ru-RU` —
   әдепкі. Бұл жобаның 2-дифференциациясын API деңгейінде бекітеді.
